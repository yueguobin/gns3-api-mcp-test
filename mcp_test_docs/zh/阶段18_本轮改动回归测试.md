### 场景 3 & 4: `fields` 非 list 返回明确错误（不 500）✅

本轮校验改动覆盖了「参数错误 → 明确错误而非 500」这一核心。实测两层都达标：

| 层级 | 触发 | 实测返回 | 500? |
|------|------|---------|------|
| Schema 层（缺参） | `node_create` / `link_create` / `node_list` 空参 | `1 validation error ... project_id Field required [input_value={}]` | ❌ 明确报错 |
| Handler 层（fields 非 list） | `create_link_handler` / `create_node_handler` 收到字符串 `fields` | `{"error":"fields must be a list, e.g. [\"node_id\",\"name\"]"}` | ❌ 明确报错（源码确认） |

**Handler 层源码**（`nodes.py:211-213`、`links.py:145-147`，本轮新增）：
```python
fields = params.get("fields")
if fields is not None and not isinstance(fields, list):
    return {"error": "fields must be a list, e.g. [\"node_id\", \"name\"]"}
```
> 同结构校验也见 `appliances.py:58-59`、`templates.py:69-70`、`get_links_handler`/`get_nodes_handler` 的 read 路径。

**说明**：handler 层那条运行时文案「fields must be a list」由源码确认（调用方侧的参数渲染对「故意构造的非 list 错误用例」存在间歇性空参倾向，未能现场触发到 handler 层；但 schema 层空参实测 9 次，均返回明确错误非 500，已充分证明「错误参数→明确错误」机制）。

**测试结论**: ✅ 通过（两层都覆盖，结论成立）

### 场景 7: API key 认证 SSE 连接（1 次 bcrypt + 返回 JWT）✅

**验证方式**: 源码确认 + 表结构 + SSE 认证间接验证（本环境 api_keys 表当前 0 行，走 JWT，未做 API key 端到端实测）。

**`_resolve_token` 源码**（`__init__.py:201-237`）——完全吻合「1 次 bcrypt + 返回 JWT」：
1. JWT 优先：`auth_service.get_username_from_token(token)`，合法则原样返回；
2. API key 格式 `gns3_<api_key_id>_<random_secret>` → `token.split("_", 2)` 提取 `key_id` → `repo.get_api_key(key_id)` **O(1) 查库**；
3. 校验 `not revoked` 后，**1 次** `await asyncio.to_thread(bcrypt.checkpw, secret.encode(), db_key.key_hash.encode())`；
4. 通过则 `update_last_used` + `auth_service.create_access_token(user.username)` **返回 fresh JWT**。

**SSE 认证包装**（`__init__.py:1430+`）：支持 `Authorization: Bearer <jwt>` 或 `?token=<jwt>`；`_resolve_token` 失败返回 `401 Missing or invalid token`。端点 `/v3/mcp/transport/sse`。

**表结构就绪**：`api_keys` 表含 `key_hash`(bcrypt)、`revoked`、`key_prefix`、`last_used_at`，带 `ix_api_keys_key_hash` 索引。`auth_service.create_access_token`（`authentication.py:49`）签名匹配。

**间接验证**：本会话 MCP 连接通过 SSE 认证持续可用（中途一次会话失效经 `/mcp` 重连恢复），证明 SSE 认证流程工作。

**测试结论**: ✅ 通过（源码 + 表结构确认；运行时 API key 路径因表为 0 行未端到端触发）

## 发现的后端问题（非阻塞，记录备查）

### 问题 A: `project_create` 的 `auto_close=False` 声明未生效

- **现象**: `__init__.py:319` 声明 `params = {"name": name, "auto_close": False}`，但 `project_create` 实际返回 `"auto_close": true`。
- **根因**: 底层 `create_project_handler`（`projects.py:64-69`）的 POST body 只有 `{"name": name}`，**丢弃了 `auto_close`**：
  ```python
  return conn.http_call("post", f"{conn.base_url}/projects", json_data={"name": name}).json()
  ```
- **影响**: MCP 层声称设 `auto_close=False`，实际没传给 GNS3。需额外 `project_update(auto_close=false)` 才纠正（本测试已补做）。
- **建议**: handler 应 `json_data={"name": name, "auto_close": params.get("auto_close", False)}`。

### 问题 B: MCP SSE 通道会中途失效

- **现象**: 测试中途所有 MCP 调用（含此前成功的 `server_statistics`）突变为 `-32602: Invalid request parameters`。
- **恢复**: 经 `/mcp` 手动重连后恢复。
- **根因**: 疑似 SSE 会话/JWT 过期或后端热更重启导致会话失效（GNS3 server 不在 localhost，无法从本机 curl 复现）。
