> **⚠️ 重要说明 — 快照操作的前置条件与恢复机制**
>
> GNS3 快照本质上是项目配置的**完整导出文件**（`.gns3snapshot` 格式），通过 `export_project()` 实现。
> 底层调用 `project.is_running()` 检查：**所有非 always-running 的节点必须处于 `stopped` 状态**。
>
> **always-running 节点**（由 `is_always_running()` 判定）在快照时被跳过检查，包括：
> `cloud`、`nat`、`ethernet_switch`、`atm_switch`、`frame_relay_switch`、`ethernet_hub`
> 这些节点由 GNS3 controller 内部管理，无独立 OS 进程。
>
> **需要 stop 的节点**（有独立进程，如 VPCS 的 `/usr/local/bin/vpcs`、Docker、QEMU、Dynamips、IOU 等）：
> 必须在快照创建前通过 `node_stop_all` 或逐个 `node_stop` 停止。
>
> **恢复机制**：`snapshot_restore` 内部执行 `close → 删除项目文件 → import 快照 → open 项目` 序列。
> 节点是否启动**不取决于快照保存时的运行状态**，而是取决于项目的 **`auto_start` 配置**。
> - `auto_start=true`（本项目配置）：open 时自动启动节点
> - `auto_start=false`：open 后节点保持 stopped

## 测试目标

验证GNS3 MCP服务器的项目快照管理功能，包括：

- **快照创建**: 在节点停止状态下成功创建项目快照
- **快照列表**: 列出项目中的所有快照及元数据信息
- **快照恢复**: 恢复到之前的快照状态，验证项目拓扑回滚
- **快照删除**: 清理不再需要的快照，释放存储空间
- **状态一致性**: 恢复前后项目配置（节点、链接）与原状态一致
- **快照生命周期**: 创建→列出→恢复→删除的完整管理周期

## 补充说明: GNS3 快照机制的技术要点

### 快照导出机制
GNS3 快照通过项目导出（export）机制实现，本质上是将项目完整序列化为 `.gns3snapshot` 文件。
这解释了为什么：
- 节点必须停止：运行中的节点有活跃进程和动态状态，无法被序列化
- 内置节点不影响：Cloud/NAT/Switch 由 controller 管理，无独立运行进程
- 快照文件可移植：理论上可以复制 `.gns3snapshot` 文件到其他 GNS3 环境

### 恢复机制
快照恢复通过 `close → 删除项目文件 → import 快照文件 → open 项目` 序列实现：
1. 关闭当前项目（close）
2. 删除项目目录下的所有配置文件
3. 从 `.gns3snapshot` 导入项目配置（节点、链接、绘图等）
4. 打开项目（open），所有节点获得与快照保存时相同的 node_id
5. **节点启动取决于项目的 `auto_start` 配置**：
   - `auto_start=true`（本项目配置）：open 时 GNS3 尝试启动所有节点
   - `auto_start=false`：open 后所有节点保持 stopped
   - 启动行为与快照保存时节点的运行状态无关

### 与手动导出的区别
- 快照: 在 GNS3 项目内管理，可通过列表查询，有专门的 API
- 手动导出: 直接导出 `.gns3` 文件到文件系统，无 API 管理
- 快照文件: `.gns3snapshot` 格式，存储在项目目录中
- 导出文件: `.gns3` 格式，用户指定存储位置

### 多快照策略建议
- 每个关键阶段创建唯一命名的快照
- 恢复前确认目标快照的正确性（通过 list 查看）
- 恢复操作不可逆（但可通过其他快照再次恢复）
- 删除快照前确认不再需要该恢复点
